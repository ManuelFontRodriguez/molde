# Adversarial review 1: agent-cost benchmark design

Date: 2026-10-15. Reviewed: the design (now `DESIGN-v1.md`) against `docs/bench/cross-framework/*`, `README.md`, `docs/reference.md`. Read-only review; nothing was run. Claude Code facts below were checked against code.claude.com/docs (headless, cli-reference) on 2026-10-15.

Verdict: the design is a good skeleton, but as written the headline result ("molde is cheaper and safer for agents") would be dismissed on three grounds: it cannot separate "molde" from "any complete checker", the grader is molde's own check list, and the incumbent ports are contrived. The harness sketch also has several flags that will not work. Fix the blocking items before code.

---

## BLOCKING (fix before any code)

### B1. The experiment cannot attribute the effect to molde's design (confounded arm), and the oracle is molde's check list
- Arm "molde" = SSG + complete check report + publish gate + MCP + a 900-line bundled reference + AGENTS.md whose "build command" is `molde check` (verification is baked into the build command). Incumbents get a build command that verifies nothing. Oracle invariants 1-5 (links, sitemap==pages, one unique title, canonical==og:url, escaping) are almost exactly `links.internal`, `sitemap.*`, `titles.*`, `canonical.*`, `og.*` in reference.md. H2 (silent failures) is then near-tautological: an agent shown a red report for the oracle's own categories cannot silently fail them. The result reads "a checker helps", which nobody disputes, not "primitives plus a report beat frameworks".
- Hostile reading of T4: five of six planted defects are 1:1 molde check ids; the sixth (double escape) is the only one outside them.
- Fix (both needed):
  1. Add ablation arms: (a) **molde-build-only** (`molde build`, no `check`, no MCP check tool, no mention of check); (b) **each incumbent + a standalone checker** that emits the same JSON report format (a ~100-line script or lychee + a small HTML linter) with equal docs. The thesis claim is only supported if molde beats (b) arms or molde-build-only loses to molde-check by a margin. Otherwise report honestly: "a complete report helps every framework".
  2. Split oracle invariants into **spec-stated** (written in the task/AGENTS.md for ALL arms as requirements: "the site must satisfy these rules") and **unstated**. Give every arm the same requirements text. Report both. Then the invariants are the task's definition of done, not molde's worldview.
- Also: the oracle must judge a fresh `molde build` (no gate), never `out/current`. With `molde check`, a failing check leaves `out/current` on the last good (stale) build; a stale pass would score as success. State the exact rebuild command per arm in the oracle spec.

### B2. The agent can see the oracle, golden and other arms; network is open
- §9 runs oracle, golden, `harness/` and all six ports in the same container/image the agent works in. With Bash and bypassPermissions the agent can `cat oracle.py`, diff against `golden/`, copy another arm's solution. Goodhart + leakage; one transcript of it kills the paper.
- Network: WebFetch/WebSearch are disallowed, but Bash `curl`/`npm install`/`pip` are not. Incumbent agents can fetch docs and packages; molde agents cannot (nothing to fetch). It also contradicts §3 ("others point at their official docs URL" while WebFetch is disallowed: the docs URL is unreachable by design).
- Env var `CLAUDE_CODE_OAUTH_TOKEN` is present in the agent's process tree; `env`/`printenv` in Bash puts a long-lived subscription token into a transcript you plan to publish (verify whether Claude Code scrubs it from Bash env; do not assume).
- Fix: agent container contains ONLY its workspace (+ toolchain, pre-installed deps, and the identical-form local docs); oracle, golden, task answers and other ports live on the host or a separate verifier container that mounts the workspace read-only after the run. Egress allowlist to Anthropic endpoints only (also set `DISABLE_AUTOUPDATER=1` and non-essential-traffic/telemetry off); `npm`/`curl` to the internet fail for everyone. Revoke the token after the campaign; grep transcripts for `sk-ant-`/token prefixes and `printenv` calls; pass the token through a file the CLI reads, not a global env if possible.

### B3. The harness sketch is wrong against real Claude Code behaviour
Checked against the docs:
- **`--bare` with a subscription fails.** Docs: bare mode "never reads OAuth credentials or the system keychain"; needs `ANTHROPIC_API_KEY`. §9's command still has `--bare` while §8 says subscription. Fix: drop `--bare`; use an empty, **per-run fresh** `CLAUDE_CONFIG_DIR` (see next point) plus `--setting-sources project` (or none), `--strict-mcp-config`, `--disable-slash-commands`. Test `--safe-mode` (docs: disables CLAUDE.md, skills, plugins, hooks, MCP, memory; auth works normally) in the pilot, and check it still honours `--mcp-config` for the MCP arm; if not, don't use it.
- **A shared empty config dir is not isolation across runs.** Without bare, auto memory is on and writes under the config dir; if the dir persists between runs, run N sees run N-1's memory. Use a fresh config dir per run (or `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`) and assert in `system/init` that no plugins/skills/hooks/MCP other than the intended ones loaded (log `plugins`, `mcp_servers`, tools).
- **Claude Code does not read `AGENTS.md`; it reads `CLAUDE.md`.** (`--bare` also skips CLAUDE.md discovery.) As written the "fair-context" file is never loaded. Fix: pass the identical-form text with `--append-system-prompt-file` (deterministic, same position for all arms) and confirm in the transcript it was received.
- **`--allowedTools` does not restrict tools** (it only pre-approves). Use `--tools "Bash,Read,Edit,Write"`. Docs also say Glob/Grep are not in the default set on Linux (Bash carries embedded find/grep), so listing them is moot; decide and state the set. Subagent (Task) and todo tools otherwise stay available and add uncontrolled tool calls/tokens; exclude them.
- **bypassPermissions as root:** Claude Code refuses `--dangerously-skip-permissions`/bypass when run as root (and sudo) outside a declared sandbox. Verify in a 1-turn smoke test; plan on a non-root user in the image. Also check `--permission-prompts none` (v2.1.259+) so an unexpected prompt cannot hang the run.
- **Model identity.** Docs describe automatic model fallback on overload and aliases that move. Pin a full model ID, pass `--fallback-model` explicitly unset/same, and read `modelUsage` keys in the result event; **fail and rerun** any run where a different model appears. Pin `--effort` (thinking tokens are in `output_tokens` and differ by effort default). Pin Claude Code version (`DISABLE_AUTOUPDATER=1`, install exact version; the tools/system-prompt change between releases).
- `--max-budget-usd` is checked against a **client-side estimate** and "spend can pass the cap"; it also works under subscription auth but the number is API-equivalent. Fine as a guard, but see I3 on censoring.

### B4. The incumbent ports are adversarial to editing: parity-to-molde-golden is the distortion, not the defence
- §10 answers "ports written by the same author" with "they already exist at byte parity". Byte parity to a golden minted from molde's own build is exactly what makes them unrepresentative: Next uses `dangerouslySetInnerHTML` template strings and a `prebuild.js` hand-writing sitemap/robots/style; Astro uses `set:html` string-building to defeat whitespace; Zola needs a `gen_content.py` data->markdown step; Hugo/Astro built-in sitemaps were rejected because their format differs from molde's. An agent editing these (T2 sectors, T3 rename, T6 pagination) pays for those contrivances and for a hand-maintained sitemap. A critic will say "you made Next.js hard to edit, then measured it."
- Also data lives in six different places (`site/data.json`, `site/data/stocks.json`, `site/src/_data/demo.json`, `src/data/data.json`, `demo/data.json` OUTSIDE the Next workspace, Zola's via generator). T1 "add a field to data.json in setup" needs per-port setup, and the Next port reads outside the git workspace (diff/`files_touched` miss it).
- Fix: make **T0 (build from empty)** a primary, co-equal result (idiomatic code, free to use built-in sitemap/head features, pass = oracle); and add an **idiomatic-port** set for T1-T9 (Next App Router components + `app/sitemap.ts` + metadata API; Astro with `@astrojs/sitemap`; Hugo built-in sitemap/canonical; Zola/Eleventy idiomatic) written or reviewed by someone other than molde's author, oracle tolerant of formatting. Report parity ports and idiomatic ports as two panels; claim only what survives both. Put all data in the workspace for every port.

### B5. No pre-registration of the analysis; pilot contaminates it; endpoints undefined
- PREDICTIONS.md is scheduled AFTER the pilot, and the pilot uses the two headline tasks (T3, T4). Design choices (tasks kept, prompts, oracle, classifier) will be tuned on those results. Commit a hashed, timestamped (tag + public push) PREDICTIONS.md and oracle before the pilot, and exclude pilot runs from the final analysis (fresh runs).
- H1 undefined: "median tool calls per *successful* change at most half the median of the five other generators". Median of what (runs, task-medians, pooled)? Which molde arm (CLI or MCP)? Choosing the better after seeing data is a forking path. Pre-specify: primary arm = molde-CLI; unit = task; statistic = per-task ratio of medians (or paired by task), pooled with a task-level bootstrap/mixed model; success = H1 upper CI bound < 0.5 vs EACH incumbent, Holm-corrected (5 comparisons).
- Conditioning on success is a survivorship bias: an arm that succeeds only on easy runs looks cheap. Report cost per attempt (all runs) as the primary and per-success as secondary; include failed runs' cost.
- H2 "lower than every other generator": zero-heavy counts. 0/10 vs 2/10 is not evidence (Fisher p=0.47). With strong models, silent failures may be rare for ALL arms (floor effect). Needs a power calculation from the pilot's incumbent rates; raise reps on T3/T4 (and on the molde-blind tasks, B6) to 15-20, or pool silent failures across tasks as the pre-specified test, with exact CIs (Clopper-Pearson/Wilson). Say in advance what "no difference" means (it falsifies H2).
- "Keep at least two of the fresh agent's tasks" is a researcher degree of freedom. Fix a rule now: ask 3 independent no-context agents (ideally a different model/vendor too) for 5 tasks each, and include every task proposed by >=2 of them that is implementable, verbatim.

### B6. T4 and the silent-failure metric favour molde; molde's blind spots are untested
- `reference.md` ("What the checks do not see") lists false-negative classes: single-quoted/unquoted attributes, relative links (`../about/`, `img.png`), CSS `url()`/`@import`, case-sensitive paths on Linux. A green `molde check` plus a broken site is exactly the failure a hostile reviewer will build, and it is a SILENT failure of the molde arm: the agent sees "pass" and says done with high confidence. The design plants only defects molde detects.
- Fix: add to T4 (or a T4b) defects in molde-blind classes (relative link, single-quoted href, CSS url(), wrong data value such as a wrong currency/ex-date copied into one page, a stale string in a template). The oracle already says "every internal href/src" so it will catch them. Pre-register the expectation "molde silent-failure rate may be higher on T4b" and publish it. This is also the best credibility move.
- The planted defects are not equally plantable: in molde, canonical/og/title come from `{{ std_head }}`; planting "missing canonical" or "wrong og:url" means bypassing the framework's own primitive (hand-written tags), which also kills title/og. Document each plant per port, randomize which template, report per-defect detection rate, not just "6 found".
- "Silent failure" semantics differ by arm: for incumbents there is no signal at all; for molde the agent must ignore a red report. Report separately: (a) agent saw a failing signal and still claimed done, (b) no signal existed. Do not merge them into one number.

## IMPORTANT

### I1. Docs asymmetry and the docs tax
- molde agents read ~800+ lines of reference (and every run pays it, including T8). Fresh-agent-per-task over-charges molde relative to real use, where docs are loaded once into a persistent project; conversely incumbents pay nothing because training covers them. Both are true; report cost split as {docs read, exploration, edit, verify} (classify tool calls by phase) and give the headline both with and without docs tokens. State the model's training prior for each framework openly (Next/Hugo/Astro in training; molde not).
- The docs mechanism must be the same *kind* for all: a local docs file of comparable size/quality per framework (e.g. the official docs' relevant pages snapshotted offline) or none for anyone. "Official docs URL" with no network is a dead pointer.
- AGENTS.md wording: freeze it, publish it, make the "build command" line the same shape for all arms (the molde line IS verification; label it so).

### I2. Arm 2 (molde MCP) fairness and cost
- MCP tool schemas (check, list_routes, explain_route, render_page, diff_build) add tokens to every turn's prefix for that arm only; report them. Run it with `--strict-mcp-config --mcp-config`; verify `mcp_servers` status connected in `system/init` and no `mcp_server_errors`.
- Tool-call counts are not comparable across arms: one `check` MCP call vs several `grep`+`cat` calls. Tool calls are the weakest metric. Prefer (primary) tokens processed and cost, (secondary) calls and turns, plus wall time as `duration_api_ms`.

### I3. Token and cost measurement under caching and budget caps
- The `result` event carries `num_turns`, `duration_ms`, `duration_api_ms`, `total_cost_usd` (client-side estimate), `usage` and per-model `modelUsage`, `permission_denials`, `is_error`, `subtype` (docs). Use the result event totals; **do not sum per-message usage** from the stream (one message split across content blocks repeats the same `message.id` and usage, so naive summing overcounts). Confirm field names in the pilot, including on `error_max_turns` and budget-cap exits.
- Cumulative `cache_read` grows quadratically with turns: it measures session length, not work. Headline unit should be "new tokens" = input + cache_creation + output, plus "total context processed" as a second; report `cache_read` separately, and cost as the API-equivalent estimate labelled as such.
- Cache state leaks across runs: the shared system-prompt prefix is warm if runs are back-to-back (5 min TTL) and cold otherwise. Randomize/interleave arm order, don't run arms in blocks; log first-turn cache hit.
- `modelUsage` can include other models (helper calls). Report them; don't silently fold.
- A small per-run spend cap censors the primary metric: heavy runs hit the cap and are "failures", which penalises exactly the arms with big contexts and truncates the data you are measuring. Set caps well above typical (pilot P95 x 3), keep `--max-turns` as the rail, and report cap/turn-limit hits as a separate outcome class (censored), not as oracle fail.
- Subscription: 5-hour and weekly limits throttle and produce `api_retry` / `rate_limit` events. Runs that fail on infrastructure (is_error, auth, 429 exhaustion, overload) must be classified `infra_fail` and re-run, never counted as agent failure or silent failure. Log retries; record wall-clock as both `wall_clock_s` and `duration_api_ms`. The quota may be shared with other interactive Claude use, so give the campaign its own window or account; and check the plan's terms for automated high-volume use before publishing a 350-run campaign (not verified here). Also: no way to reproduce on API billing unless you offer an `ANTHROPIC_API_KEY` mode; publish costs in tokens so others can price it.
- Wall-clock: dominated by model latency and queueing; build time differences (7 ms vs 1.4 s) are noise inside it. Don't headline wall-clock; if you run runs in parallel the Node builds contend for CPU and bias Node arms. Fix concurrency per arm-agnostic slot.

### I4. `claimed_done` classifier
- Headless runs almost always end with a summary claiming success; "claimed_done" will be ~100% and thus silent_failure ≈ failure rate. Define it structurally and pre-register: `claimed_done` = run ended with `subtype: success` (not turn/budget limit, not infra error) and final message does not state it was unable/blocked. Validate on a blind sample of >=40 final messages labelled by two humans without arm labels; report kappa and the classifier's confusion matrix. Publish the rule before the pilot.

### I5. Oracle validation
- Mutation test planted by the same author who wrote the oracle shares blind spots. Needed: (1) freeze oracle hash before the pilot; (2) an independent second implementation (lychee + `html5validator`/`vnu`, plus a different author or model implementing the invariants blind from the written spec) and report disagreement rate on every run's output; (3) a negative set of real agent outputs flagged by hand; (4) run the oracle on the *incumbents' own* default outputs to show it is not molde-shaped (e.g. does Next's `data-next-head`/viewport/noscript residue, `404.html` and `_next/` pages break "sitemap == pages"? `404/index.html` and `_next/data/*.json` exist in the Next export; define the HTML page set precisely: exclude 404, `_next/`, non-HTML).
- Specify expected-URL derivation (invariant 4: "page's own expected URL" = base + output path with trailing slash) per task, esp. T3 where the expected path changes, so it is a spec rule, not output-derived.
- Gaming: an agent can pass invariants by deleting pages/links or emptying the sitemap and pages together. Task assertions (page counts, content present, data-driven check: change data.json in the verifier and rebuild; the output must change) catch this; add that "mutate data -> rebuild -> pages follow" test to defeat hardcoding.
- T9 (client-side filter) cannot be judged by `html.parser`; needs a headless browser/jsdom test in the verifier (container may have Playwright; the "no browser tools" rule applies to the agent, not the verifier). T7 JSON-LD validity needs a real JSON parse and schema `@type` check in the oracle, independent of molde's `jsonld.*`.

### I6. Controls T8/T9 are weak
- H3 "molde is **no better** than the median" is satisfied by the docs tax alone (molde reads docs on every task), so passing it shows nothing about harness bias. Make controls two-sided with a stated equivalence margin (e.g. ratio within [0.7,1.4] CI) and decide in advance what failing means. T8 is only a clean control if the CSS lives at a comparable place in every port (the Next port keeps `style.css` in `demo/static/` copied by prebuild; others in `static/`/`public/`), so first make the edit locus uniform.
- T9 as "expected loss" is good for credibility but there is no JS framework baseline in the arms besides Next. Fine; just pre-register direction and judge with a real browser test.
- Add a true negative control: an arm/task where nothing is wrong and the correct behaviour is "no change needed" (does the agent over-edit?), and a null-harness check: same incumbent run twice under different AGENTS.md wording to estimate prompt-wording sensitivity (if wording alone moves cost 30%, a 2x claim is fragile).

### I7. Linux container for the build benchmark
- Claim "also answers macOS-only / non-idle machine" is overstated: colima/Docker on a Mac is a VM (virtiofs for bind mounts is slow; timings inflated and noisy), and agent runs share the host CPU. Don't run the build benchmark interleaved with agent runs; run it alone on an idle machine, report it as "Linux VM on M4 Pro", and keep the native macOS numbers. For real Linux numbers use a CI runner/VPS.
- Versions: the macOS bench pins Hugo 0.168 / Zola 0.23.6 via Homebrew; Linux apt packages differ (old, non-extended Hugo). Download the exact release tarballs for linux-arm64 (and verify checksums); same for molde (use the released `aarch64-unknown-linux-musl` binary, not a Rust toolchain in the image; no `cargo build` needed). Use `node:22-bookworm` (glibc), not alpine, for Astro/sharp and Next SWC native binaries; confirm the lockfiles carry linux-arm64 optional deps; confirm `npm ci` works offline from a pre-warmed cache. If colima defaults to x86_64 emulation, timings and Node binaries are wrong; force native arm64 (`--arch aarch64 --vm-type vz`).
- Per-run workspace copy of Next's 337 MB `node_modules` x 350 runs: use a clone-on-write overlay or read-only layer + writable upper, not `cp -r`.
- Node ports "needing network": Astro/Next may phone home for telemetry (`NEXT_TELEMETRY_DISABLED=1`, `ASTRO_TELEMETRY_DISABLED=1`) and Next fetches nothing at build otherwise; with egress locked (B2) set these or builds may stall on a DNS timeout, adding seconds and failures to Node arms only.
- Non-root user, writable HOME for the config dir and npm cache, `ulimit`/pid limits to contain runaway dev servers (an agent starting `npm run dev` or `molde serve` in the foreground blocks its Bash call until timeout: keep a Bash timeout and count it).

### I8. Reproducibility and publication
- Record and publish: full model ID, Claude Code version, image digest, tool list, system prompt additions, effort, per-run `system/init` event, all lockfiles. Repro by others costs subscription quota and is stochastic; ship `analyze.py` that reproduces every table from the published JSONL so the *analysis* is exactly reproducible even if the runs are not.
- Models change: a published "claude-opus-5-5" alias may resolve differently later; the Sonnet robustness row on the full tasks T3/T4 (not just pilot tasks) is cheap insurance, and a different-vendor row is the stronger answer to "model-specific". Say plainly the study is one vendor's agent harness.
- Privacy grep (§8) must also cover `system/init` (cwd, paths), hostnames, and the token (B2). Publish transcripts only from the clean container.

## MINOR

- Math is fine (630, 280+70=350, pilot 24; cap math is a ceiling). But §7 gives a ceiling for 350 runs and the schedule says 350; keep one number. Note the ceiling arithmetic is moot if caps are raised (I3).
- P2 only on T3/T4 (7x2x5=70) is too small to say anything about "careful" prompts; either drop P2 from the claims or run it on all core tasks for a subset of arms. On T4 ("find and fix problems") P2's added instruction is redundant.
- "Fresh agent proposes tasks" is itself Claude-distribution biased (React-heavy); fine, but say so.
- T3 realism: a real rename keeps old URLs via redirects; oracle ignores redirects. State this scope limit or add `_redirects` as an unstated-quality note (not scored).
- T0's "starting from an empty workspace that has only the framework installed": molde has no `init`-from-nothing scaffold for the agent beyond docs; define the starting files (empty dir + toolchain) identically and give the same `data.json` + spec to all. T0 diff against golden is reported but Next can't match; fine.
- Order effects: randomize run order over (arm, task, prompt, rep) with a fixed seed; log it.
- Check-first behaviour: reference.md's "diff baseline ritual: run check once BEFORE editing" is molde-specific workflow guidance that raises molde tool calls; keep it in AGENTS.md or drop it, but decide by rule, not by results.
- `--no-session-persistence` also disables transcript files on disk; you rely on stdout stream-json only. Redirect it reliably (large outputs, possible truncation at 30 s drain cap). Keep stderr too.
- Quote only medians with CIs, but add the raw per-run table and strip plots (every run visible); readers will look for outliers.
- Naming: "silent failure rate" vs "false-done rate"; pick the plain one and define in one sentence on the first line of the report.
- Hypothesis text says "five other generators" while there are six non-molde-CLI arms counting MCP; fix wording.
- Schedule: pilot to core run leaves only 3-4 working days; if the pilot shows the oracle or classifier needs changes (likely), the core run slips and external review loses its week. Consider publishing the harness + PREDICTIONS right after the pilot (also strengthens pre-registration).

## Suggested minimum redesign (one paragraph)

Arms: molde-check (CLI), molde-build-only, molde-MCP (secondary), and Hugo/Astro/Next (idiomatic) each with and without the same standalone checker; Zola/Eleventy in the parity panel only. Tasks: T0 plus T1-T6, T8, T9, plus a molde-blind T4b, each with the same requirements text for every arm. Verifier outside the agent container, with an independently implemented second checker. Primary endpoint: new-tokens per attempt, pooled over T1-T6, ratio vs each incumbent with Holm and task-level bootstrap; secondary: success rate, silent-failure split by signal present/absent. Everything frozen, hashed and pushed before the pilot; pilot runs discarded.
