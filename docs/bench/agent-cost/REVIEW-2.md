# Review 2: implementation of the agent-cost benchmark

2026-10-15. Adversarial review of the code against DESIGN.md v2. Read: DESIGN, LOG, REVIEW-1, requirements, tasks, runner/*, judge/*, oracle, checker, docker/*, solutions, ../../reference.md.

Checks run (local, no credentials): `oracle/selftest.py` (38/38), `verify_solutions.py molde` (13/13 as expected), `run_one.py --arm molde-check --task T4 --dry-run` (to inspect the context folder; results folder deleted).

Scope fact that frames everything: no agent run has ever succeeded (the only authentication test had failed, see LOG). So `metrics.py`, the Claude Code flags and the egress allow-list have never met a real transcript. Also only the `molde` port is runnable today: `PORTS` has no `idiomatic-*` entries, so `prep.py` raises KeyError for hugo, astro, nextjs and all `+checker` arms. That is fine for a work in progress; it matters because the freeze comes next.

## BLOCKING

### B1. The agent can read the planted-defect categories: `/work/context/manifest.json`
`prep.py` writes `manifest.json` into the context folder, and `run_one.py` mounts that whole folder read-only at `/work/context` in the agent container. Dry run of molde-check x T4 produced:

```
"planted": ["R2_links","R4_titles","R5_canonical_og","R3_sitemap","R6_escaping"], "workspace_commit": ...
```

An agent that does `ls /work/context` (the arm note names that folder, and `phase_of` even has a "docs" bucket for it) sees the oracle's category names for T4, `task_badge`/`task_cycle` for T4b, plus the port and the task id. This breaks the isolation promise in DESIGN §8 ("no oracle ... bench folder") and the whole T4 detection-rate result.
**Fix:** write `manifest.json` to `$out/` (not `$ctx`), or to a second mount that only the judge/metrics step sees. Keep hashes in it. Add a prep self-check that lists the files that will be mounted and asserts the set is `{arm.md, prompt.txt, bin/*, molde-reference.md, mcp.json}`.

### B2. The judge grades against the agent's own `data.json`
`judge.py` does `data = json.loads((src / recipe["data"]).read_text())` from the agent's final workspace, and the mutation test derives from it as well. The oracle's expectations (which stocks exist, their names, cycle id, yields, upcoming dividends) therefore follow whatever the agent left in the file. Examples of a wrong site that passes: on T4 delete the "AT&T Inc" row instead of fixing the double escape; on T3/T6 delete a stock; on T1 edit the yields. Not even adversarial: an agent "fixing" a failing page by editing data is a plausible strategy, and a hostile reader will find it.
**Fix:** take the reference data from the first commit (the judge already clones it for T10) plus the task's deterministic data change (`setup.DATA_CHANGES`), pass that to `oracle.judge`, and add a rule "the agent's data.json must equal the reference data on all pre-existing keys and rows" (additions of new keys allowed). Use the reference data as the base for `mutate()`.

### B3. `signal_seen` is wrong, and the (a)/(b) split of false-done is the second pre-registered headline
Three independent bugs in `metrics.py`:
1. `docs/reference.md` contains an example report with `"verdict": "fail"` (line 571). Any molde-arm run that reads the docs with `cat` or Read returns that text in a `tool_result`, and the regex marks `signal_seen = True`. The incumbents have no such file. So molde is systematically pushed from "no signal" to "signal ignored".
2. `signal_seen` means "a failing report appeared at any time". An agent that sees a red report, fixes everything, sees a green one, and is then failed by the oracle on something the checker can't see, is classed `signal_ignored`. The definition in DESIGN §7(a) is about the *last* signal before "done".
3. It scans every `tool_result`, including `grep`/`cat` of workspace files.
**Fix:** only look at results of tool calls whose input is a `molde check` / `site-check` / MCP `check` invocation (match tool_use id to tool_result id), parse the JSON, and record the verdict of the **last** such call. Report `signal_last` and `signal_ever` separately. Unit-test it with the docs text as a negative fixture.

### B4. The claim "molde-check vs incumbent + an equivalent checker" (DESIGN §1b) is not what the code builds
`site-check` covers requirements 2 to 7 and 9 with the same page-set definition, the same rules, the same strictness as the oracle (it even says so in its docstring; LOG says it was written from the same `requirements.md`). `molde check` does not see the canonical in a hand-written head, double escaping, sitemap exactness (per LOG's own measurements: 3 of the 5 T4 categories), relative links, `srcset`, or CSS `url()`. So the `+checker` arms get a checker that is a near-copy of the exam and strictly stronger than molde's; the `molde-check` arm gets a weaker one. Any result (molde cheaper/safer than hugo+checker, or the reverse) is confounded by checker strength, which is exactly what review 1 B1 warned about. Also `site-check` has a document; the incumbents' agents have never seen its output format, while the molde agent has read it in the reference.
**Fix (cheap, decisive):** add an arm `molde+checker` (molde build + `site-check`, no `molde check`) and make it the like-for-like comparator for (b). Keep `molde-check` as the "as shipped" arm. State in DESIGN that `site-check` is the stronger checker and that the oracle's rules 2 to 7 and 9 are shared with it by construction (so the +checker arms' "false-done (a)" should be near zero by design, which is a feature to be reported, not hidden).

### B5. T9 is not judged, and T8 and the Hugo/pagination paths will reject legitimate solutions
- **T9:** DESIGN §6 and `oracle.py` refer to `judge/browser_t9.py`. It doesn't exist, and no browser is in either image. The oracle's T9 check is "at least one `<input>`". Any page with an input passes; a working search can fail only by lacking an input. T9 is listed as the "expected loss" control, so a vacuous judge is worse than none. **Fix:** add Chromium/Playwright to the judge image (not the agent image), type "pep", assert the visible `<li>` set, and add a negative control solution (input with no script) to `solutions/`. If not done by freeze, drop T9 from the pre-registration instead of publishing a stub.
- **T8:** passes only if some CSS rule whose selector contains `.badge` has `color: red|#f00|#ff0000|rgb(255,0,0)` and bold. Fails: `#c00`, `crimson`, `#dc2626`, `rgb(200,0,0)` (any reasonable red), Tailwind utility classes, CSS Modules (`.page_badge__x1` does not match `\.badge\b`), inline `style=`. False pass: `background-color: red` matches `color\s*:\s*red`. The control task is supposed to have a [0.7, 1.4] cost ratio; with this judge, Next.js CSS-modules solutions will fail for a reason unrelated to cost. **Fix:** judge with the same headless browser: `getComputedStyle(.badge)` -> color hue in red range (r>150, g<80, b<80) and `fontWeight >= 700`, for every `.badge` on every stock page.
- **Hugo `/page/1/` alias (T6):** Hugo's `.Paginate` writes `/page/1/index.html` as a meta-refresh redirect stub whose canonical is `/`. `load_site` treats it as a page, so an idiomatic Hugo T6 gives "unexpected page: /page/1/", "page missing from sitemap", "no og:url". The only passing Hugo solution needs `disableAliases = true`, which an idiomatic solution doesn't have. **Fix:** in `load_site` skip pages whose only content is `<meta http-equiv="refresh">` (alias stubs) and report them as unstated notes; apply the same rule in `site-check`.
- **T2 on Hugo:** a taxonomy (`sectors`) also generates `/sectors/index.html`, which `expected_pages` doesn't list -> "unexpected page: /sectors/". Either state in `tasks/T2.md` that nothing else should exist at `/sectors/`, or allow one list page at `/sectors/`. Decide now, before the idiomatic ports exist, and test with a real Hugo solution.

## IMPORTANT

### I1. Infra vs fail classification will count rate limits and API errors against arms
`metrics.py` marks `infra_fail` only if `api_error_status` is set or `terminal_reason == "api_error"`. Claude Code reports some failures (usage limit reached, overloaded, `error_during_execution`) as `is_error: true` with other subtype/terminal_reason values or `subtype: "success"` and the message text in `result`. Those fall through to `pass`/`fail`. Also: a container OOM-kill (6 GB limit; Next.js builds are the likely victims) yields "no result event" -> `infra_fail` -> **re-run and never counted**. That is survivor bias in favour of the heaviest toolchain. **Fix:** `is_error` true (except `error_max_turns`) -> `infra_fail` unless the final text is a normal completion; match known rate-limit phrases; record `exit code 137` as its own class `oom`, and count `oom` as `fail` (it is the arm's cost), pre-registered. Validate on a smoke transcript with a deliberately bad token and a deliberately tiny `--max-turns 1`.

### I2. `claimed_done` regex is both leaky and biased
`BLOCKED_PATTERNS` is applied to the last 1500 characters. "cannot", "could not", "incomplete", "blocked" appear in normal success summaries ("the check cannot find any problems", "previously couldn't resolve ... now fixed", "the old `incomplete` page is gone"). Verbose arms (those with long JSON reports to summarise) are likelier to trigger it, so the false-done rate would shift with report style rather than with outcome. False negatives: "Done, though I wasn't able to test X" (`wasn't able` is not matched). **Fix:** pre-register the structural definition only (subtype success, not error, final message non-empty), plus the blind-labelled sample as a *validation*, not a filter; report the regex as a sensitivity analysis. Currently DESIGN says "structural" and the code is lexical.

### I3. Token accounting: `usage` of the `result` event may include or exclude auxiliary-model calls
`new_tokens` sums `result.usage`. Claude Code issues small Haiku calls (for example for tool-prefix checks); `modelUsage` is per model, `usage` may or may not include them. The code excludes Haiku from the model check, but not from the sum. Haiku calls scale with the number of Bash calls, an arm-dependent quantity. **Fix:** compute the primary from `modelUsage[<pinned model>]` only, report `usage` and the auxiliary tokens separately, and assert on the smoke run that `usage` equals the sum over `modelUsage` (or find out which it is). Also keep `thinking_tokens` out of any "ours" claim (the field name `output_tokens_details` is a guess; verify).

### I4. The molde reference lists exactly the blind spots T4b plants
"What the checks do not see" (reference.md line 647+) names relative links, `srcset`, CSS `url()` and nothing inside stylesheets: the T4b plants. The `molde-check` arm gets this file; the `+checker` arms get no equivalent note about what `site-check` doesn't see (content errors). LOG already found the section is stale for single-quoted/unquoted attributes. Result: T4b measures "can an agent follow a list of known blind spots" for molde and nothing like it for the others. **Fix:** either remove "What the checks do not see" from the benchmark copy of the reference (and say so, hash it), or give `site-check` a `not_checked` list in its output and its note (the code has `not_checked` for rules 1 and 8 already: print it in the arm note). Fix the stale claim in the reference before the freeze and say which copy was used.

### I5. Judge executes agent-written build code with the oracle mounted
`run_one.py` runs the judge container with `-v $BENCH:/bench:ro` (oracle, solutions, golden, all ports). `judge.py` runs the workspace's build command (`npm run build`, `hugo`, any `package.json` script, a Hugo module, an `astro.config` file, a molde pre-build hook) in that same container. The agent never knows the layout, so this is not a likely leak, but the design says the judge is where the oracle lives and the agent's code runs only in the agent container. A hostile reader: "build script reads /bench/agent-cost/solutions". **Fix:** build in a container without `/bench` (only the workspace and `/opt`), write the built output to a volume, then run the oracle in a second container that doesn't execute any workspace code.

### I6. Molde binary reachable from non-molde arms; forbidden-use detection is a string match
`/opt/molde-real/molde` is in every agent image. Detection is `"/opt/molde-real" in command`. `$(find / -name molde -type f | head -1) check ...` or `cd /opt/molde-real && ./molde ...` (the first contains the path only in an earlier command, the second in the same command: flagged; the first isn't). The shim for `molde-build` is bypassed by the real path; flagged only after the fact. **Fix:** don't ship the binary in the agent image. `prep.py` (judge image) copies it into `ctx/bin/molde` for molde arms (real binary or the shim wrapping `ctx/bin/.molde`), and nothing otherwise. Then the check is structural, not lexical.

### I7. Token exposure
The OAuth token is in the agent's environment (`env`, `/proc/1/environ`, and each Bash tool child). The plan (grep transcripts for `sk-ant-`) is detection after the fact, and transcripts are the published artefact; a single `env` call by an agent makes the whole run unpublishable and, because the secret regexp only covers the literal token, a base64/split echo passes. **Fix:** (a) check whether Claude Code 2.1.300 supports scrubbing credentials from tool subprocess environments (`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`; verify, don't assume) and set it; (b) otherwise start `claude` through a tiny wrapper that reads the token from a file descriptor and unsets it for children; (c) publish only after the token scan *and* a scan for the token's 12-char prefix/suffix; (d) revoke it after the campaign (already planned). `docker inspect <agent>` also shows the token while the container lives: the runner removes it right away, so say so in the docs; do not run `docker inspect` into logs.

### I8. Egress allow-list: unverified and not logged per run
`allow.txt` has only `api.anthropic.com`. The LOG test shows the host is reachable (401), not that Claude Code 2.1.300 works with only that host (OAuth profile/refresh, MCP registry, model capability lookups, telemetry hosts if `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` doesn't cover something). It's a smoke-test item. Separately: tinyproxy runs as one long-lived container; its connect log is never saved per run, so the claim "logs show what each run tried to reach" cannot be shown to a reader. **Fix:** `docker logs --since/--until` into `results/<set>/<run>/proxy.log` after every run; fail the run's `problems` if any refused host appears. Add `--cap-drop ALL --security-opt no-new-privileges` and `--cpus` to the agent container (CPU share would otherwise vary by what the host is doing).

### I9. Scored content rules outside the stated requirements (DESIGN §3 vs oracle)
DESIGN §3: "Anything the oracle grades beyond [the stated rules] is reported separately as unstated." The oracle's `check_task` **scores**, on every task: "home page shows the data's cycle_id", "the Estimated badge appears exactly when unconfirmed", "'No upcoming dividend declared.' appears when none", stock name/ticker/sector/dividend on the stock page, and the index linking each stock. None are in `requirements.md`, and the T4/T4b agents never see the T0 spec. The T4b plants `task_badge` and `task_cycle` depend on those hidden rules (the badge one is only a defect if you know the spec). **Fix:** add a requirement 10 "Content: the pages keep showing what they showed before (stock name, ticker, sector, upcoming dividend and the estimated badge rule, the cycle id on the home page)" to `requirements.md`, identical for all arms. Or move these to "unstated" and make T4b's two content plants visible by another route (a wrong value that contradicts the data on the same page, such as a ticker or amount).

### I10. T0 judging: the data path and the build command are the agent's choice, the judge's are fixed
For T0 the judge overwrites `PORTS[port]["data"]` (for the future idiomatic ports, something like `data/stocks.json` per the port factory template) and builds with the port's canonical command. The T0 prompt only says "`data.json` holds the data". An agent that leaves `data.json` at the root and reads it from there (the natural reading) is graded with a mutation written to another file: pages don't follow -> T0 fails for a correct site. The same for any T0 build that needs a generator step (as with Zola's `gen_content.py`) that the judge doesn't know. **Fix:** for T0, mutate `data.json` at the root and require that the arm note's stated build command (parsed from `manifest`/`arms.py`, which is the same text the agent was given) reproduces the site; for T1 to T10 keep the port's recipe. Add a T0 factory step that requires the idiomatic ports to read `./data.json` (simplest) so that all arms start from the same file layout.

### I11. T2 as "expected failure" needs an analysis rule, and the claim that others can do it is untested
- DESIGN §9 pools T1 to T6; LOG pre-registers that molde fails T2 *by construction*. The molde arms will then show 100% fail and 100% false-done (b) on T2 by design, pushing both pooled secondary measures. The analysis plan must say now: all pooled statistics are reported with and without T2, and T2 is its own row ("capability gap"). Otherwise a reader sees a stacked deck, and the author loses the credibility the pre-registration was meant to buy.
- LOG says "The six parity ports still pass the stricter mutation (6/6)" next to the T2 paragraph. That 6/6 is T0 (`validate_ports.sh`), not T2. `solutions/` contains only `molde.py`: no T1 to T10 solution exists for any other port, so feasibility (and oracle fairness: the Hugo alias and taxonomy cases above) on hugo/astro/nextjs is unvalidated. DESIGN §6.5 requires "passes on all correct ports"; add `solutions/idiomatic_*.py` for at least T2, T3, T6, T7, T9 before the freeze; they are also the proof the tasks are fair.
- Is T2 really impossible in molde? The test only covers `foreach` over a top-level array. If a user could precompute `sectors` with a data transform, or if molde can `foreach` a nested path, the "expected failure" is a documentation gap, not a capability gap. State in the T2 note what was tried (before publishing, run an agent without constraints on T2 as a smoke and see what it produces).

### I12. The mutation test and the page-set definition: remaining fragility
- `mutate()` writes the mutated JSON to `recipe["data"]`; if the agent moved/renamed the data file (T1 and T9 agents sometimes split data), the mutated build ignores it and the site "does not follow" -> a false fail. Detect: if the mutated build's page set equals the unmutated build's, report "mutation not applied" as `infra`, not `fail`.
- The mutated ticker `ZZZ` is appended last and uppercase; an implementation that sorts by ticker, by name or by sector passes by accident or fails T6's chunking (spec says data order). Add a second mutation that inserts a stock at position 0 with a ticker containing a dot and a digit (BRK.B-like, `A1`), and one with an empty `upcoming`.
- The page set excludes any top-level folder starting with `_` (also a legit user folder) and 404s, but nothing else (redirect stubs, `.html` fragments, Next's `_not-found`). See B5.
- Pretty-URL leniency: `resolves()` accepts `/stocks/KO` for `/stocks/KO/index.html` with a note, but `has_link` (T2, T6) requires the slash. A Hugo `.RelPermalink` has it; `next/link` without `trailingSlash` doesn't. Make `has_link` use the same leniency as `resolves`.
- T2's prompt rule is "lowercase with spaces replaced by hyphens" and the oracle uses `[^a-z0-9]+ -> -`. Same on today's four sectors, different on "Health & Care". Make the oracle implement the prompt's rule literally, or make the prompt say "non-alphanumerics".

### I13. Second judge is half-implemented
DESIGN §6.4: lychee plus an HTML validator, disagreements reported. Code: lychee output is stored; there is no HTML validator in the image, no comparison logic, and `summarize.py` merely prints the lychee counts. Also `lychee --offline` with absolute `https://demo.example/...` URLs doesn't check them (they look remote); the LOG's "0 errors out of 18 links" over six ports is therefore a statement about root-relative links only. **Fix:** `--remap 'https://demo.example/ file://<out>/'` (or `--base-url`), add `vnu` (or `html5validator`), emit `disagreements: [...]` in `verdict.json`.

### I14. Metrics never validated against a real transcript; several design promises not in code
- No unit test for `metrics.py`, no fixture transcript. Field names (`api_error_status`, `modelUsage` keys with context-window suffixes, `output_tokens_details`, `claude_code_version`) are guesses. Create a fixture from the first smoke run, commit it, and test: normal pass, max-turns, timeout (exit 124), 401, rate limit, OOM, a docs-reading run (B3).
- Promised and absent: hook/skill rejection (only plugins, tools and MCP are checked; `skills`, `slash_commands` are recorded, not enforced), budget cap (`--max-budget-usd` isn't passed), randomised order with a published seed, `analyze.py`, per-port plants chosen by seed (only molde plants exist), `site-check` in `verify_plants` for incumbents' ports (none exist), the 40-message blind sample tooling.
- Bash-timeout counting ("such timeouts are counted") isn't implemented: the transcript has the information (a tool_result with the timeout text); add it to `metrics.py`.
- `phase_of`: the "verify" regex matches the bare words `next`, `astro`, `hugo`, `npx` anywhere in a Bash command, so `cat hugo.toml`, `ls src/pages/astro`, `grep -r next` count as verifying, and `python3 build.py` counts as exploring. Anything "verifying vs exploring" derived from this will be arm-biased (framework names appear in file names). Classify by the executable: build/check commands are exactly the strings in the arm note; everything else explore. Also `/work/context` as "docs" includes `ls /work/context` and reading `arm.md`.

### I15. Reproducibility record is incomplete
`meta.json` has image ids and times. Missing for a hostile replicator: bench git commit (images were built `--allow-dirty`; the release must be a clean commit and say so in `meta`), sha256 of `oracle.py`, `site-check`, `judge.py`, `ports.py`, `requirements.md` and `reference.md` (the manifest hashes only the context), the judge's tool versions (lychee, molde, hugo in `all.txt` is in the image but not copied into the run), the docker/VM version and CPU/RAM, the proxy log (I8), the effective environment of the agent container (without the token), the seed and the schedule position. Put them in `meta.json` automatically.

- **M2.** The agent image holds every toolchain (hugo, zola, node, python, molde) for every arm. In T0 ("using the tools that are installed") a hugo-arm agent may choose Python or Zola. The arm note says "built with Hugo", but T0's prompt doesn't say "use Hugo"; add "with the build command above" to T0 or accept and report the tool actually used (derive it from `bash_commands`).

Fine for cost per change, but state "effect sizes on a 4-row dataset" prominently; a reader will ask whether costs scale. Optionally add a 40-stock dataset variant for T3 and T6 only.
- **M5.** `ensure_network` swallows failures of `docker network create`; `sh(["docker","rm","-f",PROXY])` kills a shared proxy that other concurrent runs use (the design says one run at a time; add a lock file anyway).

- **M8.** T4's "pages missing from the sitemap" for molde is `index: false`, a deliberate feature (noindex). A reader will say "that isn't a defect". Describe it as "a page left out of the sitemap by a route flag" and check that the molde reference says what `index: false` does; the agent sees a route flag with no comment.
- **M9.** `solutions/molde.py` T4/T4b solutions are exact inverses of the plants. They prove the oracle accepts the clean state; they don't prove an agent has a *discoverable* path (e.g. T4b stale cycle string: discoverable by `grep 2026-09`; badge: by reading the template). Fine, but call them "inverse-plant solutions" in docs.
- **M10.** LOG "Oracle self-test 1: 34/34 ... 22 planted defects" then 38/38: fine, but the oracle's hash is not yet recorded anywhere; add `oracle/SHA256` and check it in `judge.py` (refuse to run if different from the pinned hash, once frozen).
- **M11.** Wording that overstates in LOG: "site-check written blind" (it was given the same requirements and the molde report format, and it implements the same rule list as the oracle: it is independent code, not an independent specification). "The six parity ports still pass the stricter mutation" (T0 only, see I11). "Egress test ... reached" (reachability of one host, not Claude Code compatibility). "Isolation: ... no benchmark material" (true for the image; false for the context folder: B1).
- **M12.** `meta["agent_command"]` stores the container command including `-e CLAUDE_CODE_OAUTH_TOKEN` (name only, correct) but also the PATH and proxy settings: good for the record; add the prompt hash and the arm note to `meta` as well so the JSONL is self-contained.
- **M13.** `claimed_done` for T10 ("nothing to do"): the correct end message ("no changes needed") is treated as done; OK. But `T10` passes if `git diff` is non-empty only in invisible ways (comments, whitespace, CSS). Over-editing is reported only through visible text/titles; add `diff_lines` and `files_changed` from the archived diff to `metrics.json` and report them (the design talks about over-editing).

## What I checked and found sound
- The judge rebuilds from source with a fresh `node_modules`, a fresh molde build directory and `rm -rf` of outputs where the framework needs it; the agent's `out/current` is never read (review 1 B1 is kept in code).
- The oracle shares no code with `site-check` and no molde code; selftest 38/38; reference solutions 13/13 as expected including the negative control and the T2 expected failure.
- `docker run -e NAME` keeps the token out of the command line, `meta.json` and `docker ps`; the workspace volume and agent container are removed in `finally`.
- Ablation shim for `molde-build` refuses `check`, `mcp`, `events` and `serve --watch`, and the docs are redacted (but see below).
- Two small gaps in the redaction: the build-only reference still tells the agent to run `check` as a ritual (line 637: "Diff baseline ritual: run `check` once BEFORE you start editing"), says `check` publishes only on pass (line 553), and the "version policy" section talks about check ids. The shim answers "not available", so the agent loses a few turns reading about a command it can't use. That is a cost of the ablation, not a leak; but report the number of calls to `molde check` made by `molde-build` agents (the metrics have `forbidden_tool_use` for it), and prefer removing those lines to make the ablation clean.
