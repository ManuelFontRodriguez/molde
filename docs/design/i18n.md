# i18n: locales, localized paths, hreflang

This document records the reasoning behind molde's multilingual support: how locales are
switched on, how localized paths are produced, how translation groups and hreflang are
derived, what is checked, which alternatives were considered, and which risks were found in
review and how each was answered. For usage, see [docs/reference.md](../reference.md)
("Locales" and "Locale data").

Design constraints it honors (from the web-standards design, see
[web-standards.md](web-standards.md)): multilingual support is opt-in or nonexistent; hreflang
is a pure query over the page manifest, and its check is a set comparison. One later decision
refines the original sketch: the default locale lives at the root, and prefixing every locale
is an opt-in. (The earlier sketch prefixed all locales.)

## Worked example: a seven-language site

Take a recipe site in seven languages, with Spanish at the root, that moves to molde from
another system. Its shape, not its exact numbers, is what the design must carry.

- **Every URL has to survive the move**: about 3,000 pages, some of them noindex. A 301 is
  not free: each one risks the page's ranking.
- **Slugs are localized.** `/receta-paella/` → `/en/paella-recipe/`, `/nl/paella-recept/`,
  `/fr/paella-recette/`, `/it/ricetta-paella/`. Only a few English slugs equal the Spanish
  ones.
- **Patterns explain most slugs, not all.** For the item pages, one pattern per locale
  explains about 90% of the slugs. The rest are one-offs that an editor typed at some
  point. That's true of the default locale too.

  | | es | en | nl | it | de | fr | pt |
  |---|---|---|---|---|---|---|---|
  | pattern | `receta-{x}` | `{x}-recipe` | `{x}-recept` | `ricetta-{x}` | `{x}-rezept` | `{x}-recette` | `receita-{x}` |

- **Not every page exists in every locale.** Each translation lacks a dozen or so of the
  Spanish pages, and one lacks more.
- **A translation can outlive its original.** A few English pages translate Spanish pages
  that are no longer published, so their groups have no default-locale member.
- **Pages link across locales**: each translation names the default-locale page it
  translates, and every translated page has such a link. Those links are the hreflang groups.
- **Every slug is ASCII** (`[a-z0-9_-]`), in all 7 locales.

So a design where "path = the route pattern, prefixed by locale" is not enough: it would move
dozens of item URLs per locale, plus the other pages, in every locale including the
default. **Paths have to be data.** Patterns are the data builder's default, and an item
overrides them.

## Switching it on

```yaml
# site.yaml
locales: [es, en, nl, it, de, fr, pt]   # the first one is the default locale
prefix_default_locale: false            # default. true = /es/ as well (opt-in)
```

- No `locales:` key means there is no locale dimension: no `locale` in the context, no
  `t()`, no hreflang, and the path rule is the identity. This is the opt-in-or-nonexistent
  rule, and it holds by construction: the code path doesn't exist for such sites. Existing
  sites produce byte-identical output (pinned by a test).
- **`locale:` and `locales:` are mutually exclusive.** The existing single-language
  `locale:` key stays for single-language sites. Setting both is a load error.
- **Tags are validated by syntax, not by a registry**: a language (`es`) or
  language-REGION (`pt-BR`), case as written. `pt-br`, numeric regions (`es-419`) and
  script subtags (`zh-Hant`) are rejected until a site needs them. The path prefix is
  the tag lowercased (`/pt-br/`). The `hreflang` value and `locale` in templates are the
  tag as configured (`pt-BR`). `prefix_default_locale` without `locales:` is a load error.
- **A tag needs no formatting data to be a site locale.** Paths, hreflang,
  `t()` and `| loc` don't depend on it, so any well-formed tag loads. The data (CLDR 48,
  529 locales, generated into `src/i18n/cldr_data.rs`, see
  [cldr-formatting.md](cldr-formatting.md); it replaced seven hand-written tables for de,
  en, es, fr, it, nl, pt) gates only formatting: a `date_format` or `num_format` call that
  renders in a locale without data (the page's locale or an explicit `locale=`) is a
  render error naming the filter, the locale, the bundled CLDR version, the page and
  the template. It fails where a wrong date would print, and nowhere else. The
  single-language `locale:` key follows the same rule. An earlier iteration made a table-less
  tag a load error; that blocked sites whose templates never format in it.
- **hreflang and `alternates[].url` need `base_url`**, like `std_head` today. Without
  `base_url`, locales still expand paths and translations, but no hreflang is emitted and
  the hreflang check doesn't run.

## The path rule

A route has one of three locale modes:

| `locales:` on the route | pages | output path | in groups |
|---|---|---|---|
| absent (default) | one per site locale | the path rule below | yes |
| `[es, en]` | one per listed locale | the path rule below | yes |
| `none` | one, outside the locale dimension | the route's path, verbatim | no |

For localized routes, molde first computes an **unprefixed path** from the route, the item
and the locale (next section). Then it applies a single rule:

```
output path = unprefixed                          if locale == default and not prefix_default_locale
            = "/" + prefix(locale) + unprefixed   otherwise
```

- The rule looks at nothing else. Adding a locale can't move a default-locale page, and a
  test pins that: the default-locale paths are the same with 1 locale and with 7.
- **`locales: none`** is for things that exist once at a fixed path: `/404.html` (hosts and
  `serve` look only there), `/llms.txt`, feeds, and under `prefix_default_locale: true` the
  root `/index.html`. Such a page renders with the default locale's context (`locale`,
  `t()`), joins no hreflang group and is skipped by `html.lang`.
- **`paths.root_missing`**: under `prefix_default_locale: true`, the build fails unless a
  `locales: none` route outputs `/index.html`. That answers the contradictions of a
  prefix-all site with no root index: `href="/"` dangling, and `serve`'s `/` fallback
  finding nothing. The site decides what the root is: a chooser, or a copy of the default
  home with a canonical to `/es/`.
- **`paths.locale_prefix`**: the first segment of a default-locale unprefixed path, or of a
  `locales: none` path, must not equal another locale's prefix (the default's own prefix
  too, under `prefix_default_locale: true`). Otherwise an es page at `/it/…` shadows the
  whole Italian namespace. This is a routes-layer error, like
  `paths.duplicate`, and it runs again whenever a locale is added.
- **`paths.invalid_chars`**: every path segment, in every locale, may use only RFC 3986
  unreserved characters (`A-Z a-z 0-9 - . _ ~`). That covers the example site (all ASCII).
  Percent-encoding inside `page_url`, for non-Latin slugs, is deferred to the first site
  that needs it; until then this guard keeps invalid URLs out of canonical and hreflang.

## Routes under locales

```yaml
routes:
  - path: /index.html                 # the same unprefixed path in every locale
    template: home.html.j2
    title: "{{ t('home.title') }}"

  - path:                             # the unprefixed path per locale
      es: /contacto/index.html
      en: /contact/index.html
      nl: /contact/index.html
      fr: /contact/index.html
      # it, de, pt missing: this route has no page in those locales
    template: contact.html.j2

  - path: /{slug}/index.html
    foreach: recipes
    localized: [slug, name]           # these item fields are localized values
    template: recipe.html.j2
    title: "{{ item.name | loc }}"

  - path:
      es: /populares/index.html
      en: /popular/index.html
    template: popular.html.j2
    paginate:
      over: recipes
      per_page: 50
      path: {es: /populares/pagina/{n}/index.html, en: /popular/page/{n}/index.html}

  - path: /404.html
    template: 404.html.j2
    locales: none                     # once, at the root
    index: false
```

- **`path` as a string** means the same unprefixed path in every locale of the route.
- **`path` as a map** gives the unprefixed path per locale. Its values may contain
  placeholders (`es: /recetas/{slug}/index.html`). A locale that isn't in the map gets no
  page from this route. The map may only use site locales (`locales.unknown`).
- **`paginate.path`** may be a map on the same terms.
- **`locales:`** restricts the route (`[subset]`) or takes it out of the locale dimension
  (`none`, see the path rule). The default is every locale.

### Localized fields

A route **declares** which item fields are localized: `localized: [slug, name]`. molde doesn't
guess from the shape of the data. (A "keys are all locale tags" heuristic misreads ordinary
data at 22 locales: `id`, `no`, `is`, `it` and `hr` are all language codes.)

```json
{"recipes": [
  {"id": "paella",
   "slug": {"es": "receta-paella", "en": "paella-recipe", "nl": "paella-recept",
            "it": "ricetta-paella", "de": "paella-rezept", "fr": "paella-recette",
            "pt": "receita-paella"},
   "name": {"es": "Paella", "en": "Paella", "nl": "Paella", "it": "Paella", "de": "Paella",
            "fr": "Paella", "pt": "Paella"}}
]}
```

- **Shape.** Every item carries each declared field, as an object whose keys are site
  locales and whose values are strings or `null`. Anything else (the field absent
  included) fails the build and names the item and field. Undeclared fields behave
  exactly as today.
- **Existence.** An item exists in a locale only if **every** declared field has a
  non-null value for that locale. A missing key or `null` means no page; that's how "pt
  lacks these pages" is written in data. The one rule serves `foreach` pages and paginated
  lists alike, so a detail page is always listed, and `| loc` on a declared field never
  fails on a page that was built. (Judging `foreach` by the fields in the path alone built
  pages whose title then aborted the build, and lists disagreed with detail pages.)
- **Silent drops are made loud.** Today a missing placeholder field is an error; here a
  missing key is a legitimate "no page". So a data builder that forgets pt entirely would
  otherwise pass every check. To guard against that, `list_routes` and the check report
  show the **page count per route × locale**, and the report flags a locale whose count is
  below half the route's default-locale count (`i18n.sparse_locale`, a warning).
- **Paths.** A declared field in a path placeholder takes the page's locale value. The
  existing path-segment guard applies to each locale's value.
- **Printing.** A declared field is passed to templates and route patterns as a localized
  value that **refuses to print**. `{{ item.name }}` is a render error naming the field and
  pointing to `| loc`. Without this, a title pattern prints the object's text form, and
  7 × 400 wrong titles pass `titles.duplicate`. To use it, write `item.name | loc` (the
  page's locale) or `item.name[locale]`. The formatter only sees bare prints, so every
  other path to text (filters, `~`, `tojson`, printing the whole item) renders a
  private-use sentinel, and a page or pattern output containing it is the same render
  error. The value is opaque: it indexes, but doesn't iterate or serialize as a map.
- **Paginate.** Each locale paginates only the items that have a page in that locale,
  judged by the `localized:` declaration of the paginate route (or, if it declares none,
  every item). So a pt listing never links to a pt page that doesn't exist. Page counts may
  differ per locale.

Why the paths live in the data and not in a route pattern with exceptions: in a real site
the exceptions are about 10%. Two sources of truth for one URL (the pattern plus an override
table) is how URLs move by accident. With paths as data, the builder that writes data.json
decides, and molde renders exactly that. For new items, the site's data builder applies the
pattern (`f"{x}-recipe"`); molde never guesses.

## Translation groups and hreflang

- **`Page` gains `locale` and `group`.** Both are resolved at route expansion, before
  anything renders. The group is the set of member paths, so hreflang is a pure query over
  the manifest. No positional ID is exposed; within a build, membership
  comes from expansion, and nothing persists across builds.
- **Pages are alternates when they share a group.** That means the same route in different
  locales, plus one of:
  - the same item, for `foreach`;
  - the same page number `n`, for `paginate` (a page number beyond one locale's count has no
    member in that locale);
  - nothing more, for a static route.
- **Only indexable members count.** A page with `index: false` is not in any group's links
  and emits none. A group with fewer than 2 indexable members emits nothing.

`std_head` then emits, for each indexable page in a group of 2 or more indexable members:

```html
<link rel="alternate" hreflang="es" href="https://example.com/receta-paella/">
<link rel="alternate" hreflang="en" href="https://example.com/en/paella-recipe/">
…
<link rel="alternate" hreflang="x-default" href="https://example.com/receta-paella/">
```

- It includes the page itself, which Google requires.
- **x-default** is the default-locale member if the group has an indexable one. Under
  `prefix_default_locale: true` that's the `/es/…` page, not the root. If the group has no
  indexable default-locale member (the 3 orphaned en translations), there is no x-default.
- **Canonical stays self-referencing** in every locale, as today. It never points at the
  default locale.
- Links are reciprocal by construction, because every member emits the same set.
- **Cost.** Each alternate is about 100 B raw, so about 0.8 KB per page at 7 locales and
  2.3 KB at 22. It counts against `budgets` like any other head byte.
- **Head only, for now.** The sitemap keeps one `<url>` per page and gets no
  `xhtml:link` alternates. Google accepts any one of the methods, and using two doubles the
  bytes and the things to check. At 22 locales, a single `sitemap.xml` with alternates hits
  the 50 MB limit at about 20k URLs. Sitemap alternates remain follow-up work. The sitemap
  index (split above 50,000 URLs or 50 MB) and checks that read every child sitemap have
  since shipped.

## Template contract additions

- **New variables:**
  - `locale`: the page's tag (`"en"`);
  - `locales`: the site.yaml list;
  - `alternates`: a list of `{locale, path, url}`, one per locale version of the page,
    itself included. It keeps noindex versions (a reader can still switch to them) and
    has no x-default (not a language), so it's a superset of the set `std_head` emits.
    `url` is absent without `base_url`. Use it for a language switcher; a page that exists
    in one locale only gets an empty list.
- **`t(key, **args)`** returns the string for `key` from `translations/<locale>.yaml`.
  - `{name}` placeholders are filled from args in one pass (an argument's value is never
    scanned again); a placeholder without an argument is a render error on every page,
    whether or not that page's locale has the key. The default locale's placeholders are
    the call's contract: a translation naming a different one keeps it literal and fails
    `translations.args` (rather than aborting the render, which would hide the report).
    There is no plural logic yet.
  - In HTML output, the result is escaped like any other autoescaped value, so a
    translation can't inject HTML. Non-HTML outputs aren't autoescaped today, and `t()`
    doesn't change that.
  - `t_html(key)` is for the few strings that carry markup, and is the only unescaped path.
    Only the translation's own markup is unescaped: its arguments are escaped.
- **`value | loc`** returns the page's locale entry of a localized value. It's an error on
  anything that isn't a valid localized value, and on a value without the page's locale.
  There's no fallback, for the same reason as `t()`. It also accepts a plain map from
  `data` whose keys are all site locales: the author asked for a locale explicitly, so
  this isn't the shape heuristic rejected above (that one guessed which fields to treat
  as localized).
- **Route patterns** (`title`, `description`, `index`, `lastmod`, `jsonld`) render per page
  as today. The pattern context (`meta_ctx`) gains `locale`, `t` and `loc`, and the
  pattern environment registers the same functions and filters as the page engine. So:
  - localized JSON-LD is `"name": "{{ item.name | loc }}"`, and `inLanguage` is the site's
    business;
  - `index` and `lastmod` can differ per locale.
- **Locale filters (dates and numbers)** read `locale` from the render state instead of
  being bound once when the environment is built. An explicit argument still wins.
- **`<html lang>`**: molde doesn't write the template's `<html>` tag; the template does,
  with `{{ locale }}`. `html.lang` checks it.

### translations/

```
site/translations/es.yaml
site/translations/en.yaml
…
```

- **Optional.** With no `translations/` directory, `t()` is an error at its first use.
- **Files.** Only `<tag>.yaml` is read (`.yml` is ignored). Once the directory exists,
  the default locale's file is required, and a file for a tag not in `locales:` is a load
  error (a typo like `pt-br.yaml` would otherwise leave a whole locale untranslated).
- **Key names.** Files are flat or nested YAML, and nested keys join with dots
  (`home.title`). A flat `a.b` that collides with a nested `a: {b:}` is a load error, and so
  is a leaf that isn't a string.
- **The default locale's file defines the key set.**
  - An empty key in the default file is an error.
  - A string identical to the default's is allowed (brand names, "Nasdaq").
  - Each key's `{name}` placeholder set must match the default's (`translations.args`).
- **Unknown keys.** `t()` with a key that isn't in the default file is a report entry
  (`translations.unknown_key`: one per template and key, with the locales it was called
  in; a routes.yaml pattern is named as its route, and minijinja gives a function no
  line number, so the line is left out). It doesn't abort the render, so all layers
  still run (see the check report in [reference.md](../reference.md)). A static scan can't
  replace this, because keys can be dynamic (`t('cuisine.' ~ item.cuisine)`).
- **Missing translations.** A key that's in the default file but missing from another
  locale's file renders empty, and `translations.missing` fails the check. It never falls
  back to the default language: a silent fallback is how "half-Spanish English pages" ship.
- Key-set equality across files makes the coverage static, whichever templates happen to
  render.

## Checks

Load errors (the build doesn't start):
- `locale` and `locales` both set;
- a malformed tag (a tag without formatting data is fine, see Render errors below);
- a `path` map, `paginate.path` map or `locales:` list naming a tag not in site.yaml
  (`locales.unknown`);
- a malformed `localized:` field;
- a translation-file shape error.

Render errors (abort `check`, like any template error):
- `date_format` / `num_format` rendering in a locale without CLDR data: the message
  names the filter, the locale, the bundled CLDR version, the page (`(page /tlh/)`) and the
  template and line.

Report checks:

| check | fires when |
|---|---|
| `paths.root_missing` | `prefix_default_locale: true` and no `locales: none` route outputs `/index.html` |
| `paths.locale_prefix` | a default-locale or `locales: none` path starts with a configured prefix |
| `paths.invalid_chars` | a path segment has a character outside RFC 3986 unreserved |
| `paths.duplicate` | as today (case-insensitive), over the expanded route × item × locale set; this also catches two locales colliding on a path |
| `hreflang.mismatch` | a page's `<link rel=alternate hreflang>` set, parsed independently of attribute order and quoting, differs from its manifest group (reports `missing`, `extra`, `wrong_href`, `duplicate`, including x-default); `locales: none` and noindex pages must carry none |
| `html.lang` | on route HTML pages (noindex included; not static files or `locales: none`), the `<html lang>` value, compared case-insensitively, isn't the page's tag or a more specific tag of it (`es-ES` on an `es` page passes since #10; `en-US` fails) |
| `translations.missing` | a default-file key is absent or empty in another locale (`locale`, `key`) |
| `translations.extra` | a locale's file has a key the default file doesn't |
| `translations.args` | a key's `{name}` set differs from the default's |
| `translations.unknown_key` | `t()` was called with a key not in the default file |
| `i18n.sparse_locale` | (warning) a route's page count in a locale is below half its default-locale count |

- **`titles.duplicate`** changes scope under locales. It takes the page manifest (today it
  walks the build directory with no manifest), maps each file to its locale, and compares
  titles **within one locale**. Two locales may share a title ("Nasdaq 100"), which is a
  translation, not a duplicate.
  - Static HTML files and `locales: none` pages are compared against every locale.
  - noindex pages stay in scope, as today.
  - The remaining gap: the same untranslated data title in two locales. molde can't tell it
    from a real shared title. The data builder knows when the source system lacks a
    translation, so it owns that check. The worst case is a localized value printed raw, and
    the refuses-to-print rule stops it.
- **`description.duplicate`** gets the same per-locale scope. Its current coverage (indexable
  pages only) is unchanged.
- Without `locales:`, both checks behave exactly as today.

## Agent tooling and serve

- **`list_routes`**: `path` may now be a map, so its schema changes. Each route gains
  `locales`, `localized` and the page count per locale.
- **`explain_route` and `lookup`**: they resolve prefixed paths through `Page.path`, and
  report the page's `locale`, `alternates` and which fields were declared localized.
- **`molde serve`** is a static file server over `out/current`, so `/en/paella-recipe/`
  works without any change.
  - A miss under `/en/` gets the root `/404.html` (Spanish), exactly as the host will serve
    it.
  - There is no language negotiation, and `/` is what the site put there. Static output
    can't redirect by `Accept-Language`, and a redirect like that would hurt crawling: Google
    crawls from the US without the header.

## What this design does not do

- Plural rules, and number formats beyond decimals (percent, currency, compact) were out of
  scope at first. Formatting for any CLDR locale came afterwards, see
  [cldr-formatting.md](cldr-formatting.md).
- RTL: molde doesn't touch `<html>`; a template sets `dir="rtl"` for `ar` / `he` from
  `locale` (see "Locales" in [reference.md](../reference.md)).
- Percent-encoded (non-Latin) paths: guarded by `paths.invalid_chars` until a site needs
  them.
- Sitemap alternates: follow-up work (the sitemap index has shipped).
- Automatic translation. molde renders what the data and the translation files say.
- Moving an existing single-language site to locales. Its paths stay put by the path rule,
  but switching over is the site's decision.

## Prior art

| tool | default at root / prefix-all | localized slug | missing page | hreflang | UI strings, missing key | core? |
|---|---|---|---|---|---|---|
| [Hugo](https://gohugo.io/content-management/multilingual/) | root / `defaultContentLanguageInSubdir` | front matter per item | absent | the theme writes it | falls back quietly (warnings opt-in), CLDR plurals | core |
| [Zola](https://www.getzola.org/documentation/content/multilingual/) | root / no | `path` per item | absent | the theme writes it | `trans()`, no plurals | core |
| [Eleventy](https://www.11ty.dev/docs/plugins/i18n/) | DIY | via directories | `errorMode` (strict or fallback) | the theme writes it | none | bundled plugin |
| [Astro](https://docs.astro.build/en/guides/internationalization/) | root / `prefixDefaultLocale` | DIY | redirect or rewrite fallback | sitemap only | none | core routing |
| [next-intl](https://next-intl.dev/docs/routing/configuration) | `always` by default | `pathnames` pattern | the app decides | `Link` header | ICU | library |
| [Nuxt i18n](https://i18n.nuxtjs.org/docs/guide) | 4 strategies | per-route pattern | `fallbackLocale` | `useLocaleHead()` | vue-i18n, plurals | module |
| [Docusaurus](https://docusaurus.io/docs/i18n/tutorial) | root | mirrored files | falls back | automatic, with x-default | ICU | core |
| [Polylang](https://polylang.pro/documentation/support/guides/url-modifications/) / [WPML](https://wpml.org/documentation/getting-started-guide/language-setup/language-url-options/) | root or directory | yes | fallback optional | automatic | .po | plugin |

**Where this design agrees with common practice.**
- The default locale at the root, with prefix-all as an opt-in (Hugo, Zola, Astro, Docusaurus, Nuxt `prefix_except_default`, Polylang "hide default").
- Localized slugs are per-item data (Hugo `slug`/`url`, Zola `path`, WPML). Per-route patterns (Nuxt, next-intl) still need per-item slug data for dynamic pages, and they can't express the 10% irregular slugs.
- A missing locale means no page (Hugo, Zola, Eleventy strict).
- Automatic hreflang in `<head>`, with x-default set to the default locale (Docusaurus, Nuxt). Google accepts the head, an HTTP header or the sitemap as [equivalent](https://developers.google.com/search/docs/specialty/international/localized-versions).
- i18n in core, but opt-in.

**Where it's stricter, and why.**
- **No fallbacks, for pages or strings.** Hugo, Docusaurus, vue-i18n, Astro `rewrite`, Polyglot and WPML all fall back by default. That serves default-language content under `/fr/` URLs. It's the most reported pitfall: duplicate content, and "half-translated" pages that nobody notices. molde fails a check instead. Identical strings, such as brand names, are allowed as values.
- **hreflang covers indexable members only.** Most tools link noindex pages too, and Google reports that as an error.
- **The hreflang set is checked against the manifest.** None of the surveyed tools ship this. It enforces Google's reciprocity and self-reference rules at build time.

**Considered and not taken.**
- **An explicit group key**, like Hugo's `translationKey`. Here a group is route × item, and the data builder merges translations into one item. The example site's source data already links translations to their default-locale page, so the builder does exactly that. Revisit it if a real case needs to link items across routes.
- **An hreflang value separate from the path segment**, like Docusaurus `htmlLang` (path `es`, hreflang `es-ES`). A config tag `es-ES` already gives `/es-es/`. Add a per-locale override only when a site needs it.
- **Plurals.** When they come, use CLDR categories (`one/few/many/other`) as keys under the message, so existing yaml files stay valid.

## Risks considered

An adversarial review of the design produced these findings. Each is answered in the design
above.

| # | finding | severity | where it's answered |
|---|---|---|---|
| R1 | the path rule contradicted root-only routes | blocker | `locales: none`; `paths.root_missing` in the checks table |
| R2 | a single sitemap with alternates doesn't scale | blocker | head-only hreflang for now; sitemap alternates are follow-up work (the index has shipped) |
| R3 | localized values printed raw in patterns | blocker | declared fields refuse to print; `meta_ctx` gains `locale`/`t`/`loc` |
